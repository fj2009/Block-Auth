1. Resumen ejecutivo

Este proyecto implementa un sistema de autenticación y autorización descentralizado cuya fuente de verdad para identidades, credenciales y permisos reside en una blockchain Ethereum local, en lugar de un servidor central de identidad (RADIUS, Active Directory o la propia tabla users/roles de una base de datos). El objetivo práctico es gobernar el acceso a una base de datos — quién puede leer, escribir o borrar cada tabla — eliminando el punto único de fallo del modelo centralizado y blindando la autenticación frente a ataques de denegación de servicio (DoS).

El sistema se construye como un MVP demostrable sobre una red local de coste cero (sin gas, sin dependencia de internet): usuario → Proxy Validador → base de datos. El Proxy es la única puerta: verifica la identidad del usuario (firma digital sobre la petición), comprueba sus permisos contra la blockchain y solo entonces ejecuta la consulta con un usuario de base de datos restringido.

2. Motivación y problemática

2.1 El punto único de fallo de la identidad centralizada

Los modelos clásicos de control de acceso — RADIUS en redes cableadas/IP, Active Directory en entornos corporativos, o la tabla de usuarios del propio SGBD — concentran toda la decisión de acceso en un único servidor. Esta concentración tiene tres consecuencias estructurales:

  • Disponibilidad: la caída del servidor de identidad bloquea toda la autenticación (la red se queda sin accesos legítimos).
  • Resiliencia ante DoS: un ataque de denegación de servicio dirigido al servidor de identidad paraliza el sistema completo; el atacante solo necesita robar un punto.
  • Confianza y privacidad: el servidor central conoce todas las credenciales; un robo de esa base equivale al robo de todas las identidades.

2.2 Por qué blockchain aporta una alternativa

Una blockchain permisionada o local aporta tres propiedades a la decisión de acceso:

  • Estado distribuido: la misma verdad sobre identidades y permisos se replica en varios nodos; no existe un único servidor que derribar.
  • Inmutabilidad y auditoría: cada concesión, revocación o rotación de clave queda registrada en un ledger que no se puede alterar retroactivamente.
  • Soberanía del usuario: el portador de la identidad firma sus propias peticiones con su clave privada; el sistema nunca almacena claves de usuario.
Delimitación: el MVP usa una red local de un nodo (Hardhat) para demostrar el mecanismo; la mejora a varios nodos (p. ej. Besu IBFT) está prevista en la hoja de ruta (sección 16), sin cambios en los contratos.

4. Estado del arte: Identidad Autosoberana (SSI)

El modelo SSI (Self-Sovereign Identity), estandarizado en el W3C, invierte el control de la identidad: el sujeto es el holder de sus credenciales y las presenta bajo demanda, sin que un servidor central las custodie. Se apoya en tres piezas:

Trinidad técnica W3C aplicada al proyecto
PiezaRol en el papelImplementación en el MVP
DID (Decentralized Identifier)Identificador único, permanente y verificable del sujeto.did:web:tfg:demo:doctorA; en el registro se almacena keccak256(DID). (DEC-08)
VC (Verifiable Credential)Atributo firmado por un emisor (RRHH, IT). En el MVP el "rol" se modela como una política de organización firmada por el admin (assignRole). Extensión a VC completas prevista (sección 16).
VP (Verifiable Presentation)Prueba criptográfica de que se posee el atributo. Firma EIP-191 sobre la petición (payload + nonce + timestamp) con la clave de la wallet.

6.2 Flujo de autenticación y autorización

P1  Usuario:  payload = { sql, nonce, ts };  firma = Sign(keccak(payload))  [wallet]
P2  Proxy:    valida ts (±30 s) y nonce (no repetido)                        [sin gas]
P3  Proxy:    owner de la identidad (caché → on-chain si miss)               [view]
P4  Proxy:    ¿isRevoked?  ¿can(did, tabla, operación)?                      [view]
P5  Proxy:    OK → JWT de sesión (rol, did, exp) y ejecución en BD con el
              usuario restringido del rol correspondiente
P6  Proxy:    devuelve filas/error
P7  Async:    suscripción a eventos Revoked / RoleRevokedFor → invalidación
              de caché y de sesiones del DID afectado

8. Módulo 2 — Contratos de identidad, revocación y permisos

El Módulo 2 convierte el stub en la fuente de verdad completa. Tres contratos con responsabilidades separadas para responder a tres preguntas distintas: ¿quién eres?, ¿estás expulsado? y ¿puedes hacer esto?.

8.1 IdentityRegistry — identidad y rotación de clave

  • DEC-08: cada DID (hash) se asocia a una dirección Ethereum (clave secp256k1 de la wallet del usuario).
  • registerDID(didHash, owner): solo ADMIN_ROLE; rechaza duplicados.
  • rotateKey(didHash, newOwner, sig): autogestión — quien posee la clave ANTIGUA firma (EIP-191/eth_sign) el payload keccak256(didHash, newOwner); el contrato recupera la dirección con ECDSA.recover. Sin intervención del admin (soberanía).
  • deactivate(didHash): kill-switch administrado e irreversible.
  • Vistas sin gas: isRegistered, isDeactivated, getOwner.
  • Eventos: DIDRegistered, KeyRotated, IdentityDeactivated.

8.2 RevocationRegistry — revocación irreversible

  • revoke(didHash): solo REVOKER_ROLE (rol concedible a más operadores por el admin). Emite Revoked — el evento que el Proxy escucha para invalidar caché y sesiones.
  • isRevoked(didHash): vista sin gas.
  • Semántica: irreversible (expulsión / clave comprometida). Es la pieza crítica de cualquier sistema descentralizado: aquí la revocación es inmediata, auditable y propagable.

8.3 AccessPolicyRegistry — RBAC descentralizado

  • Roles de organización: ROLE_ADMIN, ROLE_WRITER, ROLE_VIEWER, ROLE_ANALYST.
  • Operaciones como bitmask: OP_READ=1, OP_WRITE=2, OP_DELETE=4.
  • setPolicy(rol, tabla, ops): solo admin; define la matriz rol→tabla→operación.
  • assignRole(did, rol) / unassignRole(did): reversibles; emiten RoleGrantedFor/RoleRevokedFor.
  • can(did, tabla, op): oráculo de autorización, vista sin gas, usada por el Proxy.
  • DEC-09: nombres propios para evitar colisión ABI con AccessControl.grantRole.

9. Módulo 3 — Proxy Validador (diseño cerrado)

Componente central para responder a la pregunta más esperada del tribunal: "¿una consulta a la blockchain no tarda 2 segundos frente a los 10 ms de RADIUS?". La respuesta es arquitectónica: la blockchain nunca está en el camino crítico.

Estrategia de latencia del Proxy
MecanismoEfecto
Caché TTL (30 s) de estado on-chainIdentidad/rol/revocación verificados una vez, reutilizados N veces (cache hit).
Token de sesión JWT efímero (60–120 s)Consultas sucesivas del mismo usuario = validación local (~milisegundos).
Vistas sin gas (lecturas)Los miss de caché no pagan consenso: solo un eth_call.
Listener de eventos RevokedLa revocación se propaga en < 2 s invalidando caché y sesiones.
Fail-closed / fail-open por recursoCon la cadena caída pero caché caliente, el acceso continúa; decisión política.

Elección del tribunal: PostgreSQL 16 en Docker como base de datos protegida. La defensa se apoya en defensa en profundidad: el Proxy es la puerta lógica y el SGBD la red de seguridad.

12. Seguridad en el diseño

Matriz de amenazas y mitigaciones
AmenazaMitigación
Bypass del Proxy (conexión directa a BD)Red interna Docker + usuario único de BD con grants mínimos (sección 10).
Replay de petición firmadaNonce (memoria del Proxy) + ventana temporal ±30 s.
Robo de clave de usuarioRotación autogestionada (rotateKey) + revocación irreversible de identidad (RevocationRegistry).
Revocación tardía de permisosJWT corto + invalidación por eventos (< 2 s).
DoS al servidor de identidadNo existe: la verdad está replicada/validable en la capa blockchain; el Proxy es stateless y escalable.
Escritura maliciosa / fugaTraducción rol→grants + validación de query + grants mínimos.
Alteración retroactiva de permisosLedger inmutable; cada acción emite evento auditable.

14.1 Lecciones transversales

  • No desactivar las políticas de seguridad de npm; aprobar el paquete exacto.
  • Conocer los tipos de retorno de ethers (hex vs. binario) antes de escribir tests.
  • Gestión de procesos por PID, nunca por patrón que esté en la propia línea de comandos.
  • Preferir JSON-RPC crudo cuando se necesite un estado exacto y vigente de la red.
  • Releer la documentación de la versión concreta de cada librería (OZ 5.6, HH3).
